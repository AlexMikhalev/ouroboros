# 13. External Skills Layer

The skill plane outside the runtime package lives here: where built-in and installed payloads live, the independent gates between installation and execution, and how archive installs, declared dependencies, extension staging and the bundled Telegram transport are admitted. Discovery, review, grants, dependency readiness and enablement stay separate facts, because collapsing any two turns a UI toggle into execution authority.

### Skill gates

Payloads live in data-plane buckets under `data/skills/`; review, install record, grants, enablement, dependencies, tokens and health under `data/state/skills/<name>/` (§1 Data layout). Discovery confers no trust (§6 Skills and extensions); a conflict declared by either enabled peer is enforced symmetrically without deleting either payload. The executable sequence is install → deterministic preflight → digest-bound review or acceptance → grants → dependency readiness → enablement → execution; the gates stay independent (§10 invariant 8): a review PASS installs no dependencies, `enabled=true` does not prove readiness, and an extension additionally needs host registration. Mutating lifecycle work flows through one deduplicated queue (`skill_lifecycle_queue.py`); a review panel lends the lane out and persists only while its bytes are installed; review jobs keep their full record privately, and the compact UI history projects a `running` job with a dead process or stale heartbeat as `interrupted` without writing, while the Skills list read heals and syncs nothing. Review ordinals are allocated only after a job starts under the lifecycle lock, so retry history stays explainable without a UI counter becoming review authority.

Execution resolves one selected canonical directory through the full loader on every request. Conflict checks use a fresh immutable peer projection (`skill_peer_inventory.py`); peer payloads are not hashed and no partial executable object is synthesized. The verdict is one duck-typed function (`skill_conflicts.py`), so the full loaded skill and the cheap peer descriptor cannot reach different answers. Selected payload and peer projection are refreshed again after slow lifecycle reconciliation, so a cross-process disable, revoke or same-size restored-mtime edit takes effect on the next request; a valid manifest keeps its declared conflicts even when its payload is unreadable.

### Skill review authority

These gates govern installed-skill activation. A reviewer's configured rights separately govern checks of untrusted code in its private copy: Full is not an OS sandbox, and checking grants no skill activation.

Skill review combines deterministic preflight with independent multi-model feedback; a deterministic preflight failure persists as PENDING, not as advisory-overridable BLOCKERS. Records bind the release digest (`skill_identity.py`: payload plus declared dependencies, per-install notes out); a one-time conversion moved records covering unchanged bytes. Without a review, only host-owned facts admit exact bytes (`skill_acceptance.py`): a trusted source's install record, the owner's Skip review, or an owner edit by the selected-skill task the owner's door started. A review-each source keeps blockers off even under Advisory, author finish included. Elsewhere under Advisory an explicit author finish may accept current bytes after prior substantive feedback, or with an exact returned terminal job/hash reference carrying partial feedback or disclosed review unavailability; each finish runs current preflight and records its proof in `author_disposition.review_reference`, and a running critic without feedback is not "unavailable". `SkillReviewState.gate_for` gives every consumer the same current authority; critic hash, status and findings never change. Blocking always needs fresh critic approval; Cyber keeps its P0/P3 judgment. Hub publication reuses this authority (§6 Skill publication).

### Telegram built-in

`skills/telegram/` owns the in-process bridge and supervised companion (sidecar/tunnel/menu rollback/heartbeat/singleton). Text needs no tunnel. The built-in (`skill_builtin.py`) needs grants; Colab waits for its executable install, grants missing eligible items under owner auto-grant, then enables. `data/state/skills/telegram/` keeps binding, companion, rollback, cursors, tunnel cache and bounded derived message references; map write faults warn, never stop delivery. Confined files enter `/chat/inject` then `data/uploads`; quiz answers use `/chat/decision`. Other replies carry row/work facts, never routing; status notices reference work, not Main's unseen answer. Earlier same-chat owner messages get native replies. Continue messages stay separate; relay success is silent, failure one line. Oversized files point in-app or to an active Mini App, without starting tunnels or publishing URLs. `lib/telegram_i18n.py` uses `OUROBOROS_UI_LANGUAGE` (§7), preserving host lines; `/language` uses Host `/ui/language`. The completion toggle gates terminal/Main status notices; Off consumes IDs. Replay enriches `completion_notice` (§3), not text. Silent Mode, replies/files/quizzes and salvage stay independent; events only wake one `TypingCue` over `ouroboros/gateway/reply_preparation.py` (DESIGN §9). `TELEGRAM_PROXY` covers Telegram API only, otherwise egress is direct; dependency locked `httpx[socks]`. Limits/proxy forms: `skills/telegram/SKILL.md`.

`list_skills` projects lifecycle state through `skill_catalogue.py`: without a name, sorted pages of whole compact records include disabled, unreviewed, broken and colliding skills, with counted preview omissions. Its snapshot detects membership changes, not payload or state edits; pages are not an atomic state view. `list_skills(name=...)` returns full diagnostics and the exact `manifest.read` call for the loader-selected physical `SKILL.md` or `skill.json`; instructions stay at that source. An unreadable extra payload file does not hide a readable manifest, while an unparsed manifest or colliding name has no manifest address. Unknown names return `found: false`, and oversized details use the generic result source. `model_experience` also reaches the bounded installed-skills context; each `SkillManifestError` carries its repair `fix_hint`.

### Sources, installs and dependencies

Sources are one owner list (`skill_sources.py`); a row's trust becomes an install's basis, never rewritten. Git sources are shallow cache clones under `state/skill_sources/`, fetched in the background with host credentials (`skill_source_git.py`); a hub (`hub.json`) gives entries, digest-bound Official endorsements and categories, a plain repository its manifest folders (`skill_source_catalog.py`). One lifecycle serves every source (`skill_source_install.py`): the copy must match its release digest, lands under `install.PayloadRollbackSnapshot`, writes `install.json`; `trusted` keeps the deterministic preflight before grants, dependencies and turn-on-when-ready, `review` starts a review. Updates name the candidate digest; a modified copy offers replace, keep or an owner-door merge. ClawHub archives land atomically with per-file hashes. Install metadata drives isolated dependencies (`marketplace/install_specs.py`; manual instructions stay guidance); accepted hash-covered declarations authorize literal build/check argv, caches persist in `state/skills/<name>/dependency_cache`, `deps.json` records results; an absent check stays unknown, output drift invalidates readiness. Publication: §6; `provenance.py` clears only the local receipt. Script runtimes: `tools/skill_exec.py`, `docs/CREATING_SKILLS.md`.

### Tool result views

Result composition and the `PRODUCER_RESULT_SOURCE_JSON` / `FULL_RESULT_SOURCE_JSON` distinction: `tools/tool_result.py` and `loop_tool_execution.py`.

### Extension import and isolation

Extensions import through staged trees (`_stage_extension_import_tree` under `__extension_imports/`), so concurrent workers cannot remove a peer's live import and stale trees stay reclaimable. Per-call child processes may proxy tools, routes, WS, UI, settings and companion descriptors, while persistent subscriptions and supervised tasks need in-process or companion lifecycle; the generic capability matrix reports which, never a platform name. Isolated children run the same staged loader in a private base with a scrubbed env, so native crashes cannot kill `server.py`. In-process extensions are the powerful path, so namespacing, declared permissions, per-skill tracking and atomic unload are an executable contract, not convention. Skill repair enqueues an ordinary managed task admitted against one exact payload revision (`skill_repair_admission.py`; §6 Skills and extensions); a `skill_repair` constraint, still produced by the bucket + skill-name short form and canonicalized to `normal` at promotion, selects the payload only and grants no reduced tool profile. An installed payload needs no Git copy, and review never forces unload merely because the caller is repairing it.
