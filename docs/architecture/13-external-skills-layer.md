# 13. External Skills Layer

The skill plane covers built-in and installed payloads, dependencies, extension staging and Telegram. Discovery, review, grants, readiness and enablement remain separate facts because collapsing any two turns a UI toggle into execution authority.

### Skill gates

Discovery confers no trust; a review PASS installs no dependencies; `enabled=true` does not prove readiness. Payloads live under `data/skills/`; lifecycle state under `data/state/skills/<name>/` (§1). The sequence is install → deterministic preflight → digest-bound review or acceptance → grants → dependency readiness → enablement → execution; extensions also need host registration (§10 invariant 8). Either enabled peer's declared conflict applies symmetrically without deletion. One deduplicated queue (`skill_lifecycle_queue.py`) owns mutations. Panels lend the lane and persist only for still-installed bytes. Review jobs keep full private records; UI history projects dead-process/stale-heartbeat jobs as interrupted without writing. Skills list reads heal nothing. Ordinals are allocated under the lifecycle lock after job start, so retry history stays explainable without a UI counter becoming review authority.

Execution resolves one selected canonical directory through the full loader on every request. Conflict checks use a fresh immutable peer projection (`skill_peer_inventory.py`); peer payloads are not hashed and no partial executable object is synthesized. The verdict is one duck-typed function (`skill_conflicts.py`), so the full loaded skill and the cheap peer descriptor cannot reach different answers. Selected payload and peer projection are refreshed again after slow lifecycle reconciliation, so a cross-process disable, revoke or same-size restored-mtime edit takes effect on the next request; a valid manifest keeps its declared conflicts even when its payload is unreadable.

### Skill review authority

These gates govern installed-skill activation. A reviewer's configured rights separately govern checks of untrusted code in its private copy: Full is not an OS sandbox, and checking grants no skill activation.

Preflight failure persists as PENDING, never advisory-overridable BLOCKERS. Records bind the release digest (`skill_identity.py`: payload plus dependency declarations, without install notes); conversion rebinds only proven unchanged bytes. Host facts admit exact bytes without a panel: trusted source, recorded `self_check`, owner Skip, or owner edit by the owner's selected-skill task. In ordinary tasks, owner-requested edits use existing `skill_owner_action` Skip with `owner_source` carrying the owner's words. Edits invalidate earlier acceptance. Review-source blockers stay off under Advisory, author finish included. Elsewhere Advisory author finish accepts after substantive feedback or an exact terminal job/hash reference carrying partial feedback or disclosed unavailability; it runs preflight and records `author_disposition.review_reference`. A running critic without feedback is not unavailable. `SkillReviewState.gate_for` supplies one authority without rewriting critic facts; Blocking needs fresh approval, Cyber keeps P0/P3 judgment. Publication: §6.

### Telegram built-in

`skills/telegram/` owns the in-process bridge and supervised companion (sidecar/tunnel/menu rollback/heartbeat/singleton). Text needs no tunnel. The built-in (`skill_builtin.py`) needs grants; Colab waits for its executable install, grants missing eligible items under owner auto-grant, then enables. `data/state/skills/telegram/` keeps binding, companion, rollback, cursors, tunnel cache and bounded derived message references; map write faults warn, never stop delivery. Confined files enter `/chat/inject` then `data/uploads`; quiz answers use `/chat/decision`. Other replies carry row/work facts, never routing; status notices reference work, not Main's unseen answer. Earlier same-chat owner messages get native replies. Continue messages stay separate; relay success is silent, failure one line. Oversized files point in-app or to an active Mini App, without starting tunnels or publishing URLs. `lib/telegram_i18n.py` uses `OUROBOROS_UI_LANGUAGE` (§7), preserving host lines; `/language` uses Host `/ui/language`. The completion toggle gates terminal/Main status notices; Off consumes IDs. Replay enriches `completion_notice` (§3), not text. Silent Mode, replies/files/quizzes and salvage stay independent; events only wake one `TypingCue` over `ouroboros/gateway/reply_preparation.py` (DESIGN §9). `TELEGRAM_PROXY` covers Telegram API only, otherwise egress is direct; dependency locked `httpx[socks]`. Limits/proxy forms: `skills/telegram/SKILL.md`.

`skill_catalogue.py` projects lifecycle state: `list_skills` returns sorted pages of whole compact records, including disabled, unreviewed, broken and colliding skills, with counted preview omissions. Snapshots detect membership, not payload/state edits; pages are not atomic. `list_skills(name=...)` gives full diagnostics and `manifest.read` for the loader-selected `SKILL.md` or `skill.json`; instructions stay there. An unreadable payload file does not hide a readable manifest; an unparsed manifest or colliding name has no manifest address. Unknown names return `found: false`; oversized details use the generic result source. `model_experience` reaches bounded installed-skills context; each `SkillManifestError` carries its repair `fix_hint`.

### Sources, installs and dependencies

Sources share one owner list (`skill_sources.py`). Suggested trust applies until chosen: Official without review, Community review each; later trust changes affect new installs, not existing records. Git caches in `state/skill_sources/` use host credentials; hubs supply entries, digest endorsements and categories, plain repositories their manifest folders. `skill_source_install.py` verifies releases and records their install basis. Ouroboros chooses `check: review` (configured panel) or `self` (read exact release, record 1–2000 character notes), judging what the skill can touch. Trusted sources ignore check depth. HTTP shapes: `ouroboros/gateway/skill_source_contracts.py`.

Updates compare candidate and optional local digests. Replace keeps `.previous`; keep skips; merge uses the owner's task door. Review-basis replacement durably keeps the previous payload and lifecycle state; `pending_update` names its candidate. Completion, owner Skip and background startup without a live review settle in the lane: accept executable bytes, otherwise restore and reconcile, recording `update_rejected` for review, preflight or landing/dependency failure. Superseded snapshots cannot restore over newer installs; partial restores retain evidence and never replace the payload twice. Owner Update without review binds `owner_skip` to the exact release. Starter ids accept any source; absent/blank selects defaults, `[]` none. `OUROBOROS_STARTER_SKILLS_TURN_ON` defaults true (§7); built-ins precede git fetches.

ClawHub archives land atomically with per-file hashes. Accepted dependency declarations authorize literal build/check argv (`marketplace/install_specs.py`); manual instructions stay guidance. Caches live in `state/skills/<name>/dependency_cache`, results in `deps.json`; absent checks stay unknown and drift invalidates readiness. `provenance.py` clears only the local receipt. Script runtimes: `tools/skill_exec.py`, `docs/CREATING_SKILLS.md`.

### Tool result views

Result composition and the `PRODUCER_RESULT_SOURCE_JSON` / `FULL_RESULT_SOURCE_JSON` distinction: `tools/tool_result.py` and `loop_tool_execution.py`.

### Extension import and isolation

Extensions import through staged trees (`_stage_extension_import_tree` under `__extension_imports/`), so concurrent workers cannot remove a peer's live import and stale trees stay reclaimable. Per-call child processes may proxy tools, routes, WS, UI, settings and companion descriptors, while persistent subscriptions and supervised tasks need in-process or companion lifecycle; the generic capability matrix reports which, never a platform name. Isolated children run the same staged loader in a private base with a scrubbed env, so native crashes cannot kill `server.py`. In-process extensions are the powerful path, so namespacing, declared permissions, per-skill tracking and atomic unload are an executable contract, not convention. Skill repair enqueues an ordinary managed task admitted against one exact payload revision (`skill_repair_admission.py`; §6 Skills and extensions); a `skill_repair` constraint, still produced by the bucket + skill-name short form and canonicalized to `normal` at promotion, selects the payload only and grants no reduced tool profile. An installed payload needs no Git copy, and review never forces unload merely because the caller is repairing it.
